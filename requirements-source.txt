Core thesis: Build the forensic recovery engine first. Treat vendor-specific parsers as validated adapters, not 
as the foundation. Keep original evidence immutable; recovery, inference, and visual enhancement must 
remain explicitly separated.
1. Executive Summary
The proposed product is a desktop-first forensic evidence platform for DVR/NVR storage. It accepts a physical 
storage device or a forensic image, performs read-only acquisition and health checks, analyzes 
partition/filesystem structures, discovers recoverable media and metadata, attempts deterministic 
reconstruction where structural evidence survives, falls back to generic raw-data recovery for 
unknown/proprietary layouts, and uses validated vendor/format adapters when deeper metadata extraction is 
possible.
The architecture is deliberately inspired by proven patterns from existing forensic products: case-centric 
evidence handling and reporting; disk-image and filesystem analysis; modular ingest/analyzer pipelines; 
proprietary DVR demuxing and conversion; multi-source timeline/review; and non-destructive, auditable 
enhancement. These patterns should be adopted conceptually, not copied as product code or UI.

3. What the Product Should Actually Solve
 Normal exported video that fails to open because the container/index/finalization was damaged.
 Interrupted DVR writes after power loss or recorder shutdown.
 Deleted recordings whose media bytes or metadata still remain on storage.
 Corrupted partitions/filesystem metadata where raw data is still readable.
 Partially recoverable recordings where only fragments or intervals survive.
 Unknown or unsupported vendor formats where generic recovery can still attempt to recover standard 
video structures.
 Targeted recovery: retrieve the relevant camera/time/event without forcing the examiner to process every 
recovered clip manually.
 Best-available-quality recovery when main stream data is damaged but a secondary stream, snapshot, 
thumbnail, or related metadata survives.
 Forensic reporting with hashes, acquisition details, recovery source, validation status, gaps, and processing 
history.

6. Recovery Engine - Three Tiers
Tier 1 - Deterministic structural recovery
Search for primary/backup indexes, journal remnants, filesystem metadata, vendor metadata, allocation 
records, timestamps, and integrity fields. If these structures explicitly map recordings to storage regions, follow 
the mapping directly.
Evidence -> structural scan -> surviving index/metadata -> exact sector/fragment map -> reconstruct -> validate
Tier 2 - Verified fragment reconstruction
When a direct index is unavailable, create a fragment database. Candidate relationships can use channel 
identifiers, codec parameters, timestamps, frame ordering, neighboring structure, and other format evidence. 
Use a decoder as a validation gate, not as the only proof.
Fragments -> compatibility filters -> candidate edges -> score/rank -> decode-test seams -> accept/reject -> assembly
Tier 3 - Partial/degraded recovery
When complete reconstruction is impossible, preserve every independently valid fragment. Represent missing 
intervals in the timeline rather than silently filling the evidence with fabricated frames. Export recovered 
segments separately and label them clearly.
Recovered segment A -> export
Missing interval -> explicit timeline gap
Recovered segment B -> export
Original evidence remains untouched

8. Parity / ECC / Redundancy - Correct Scope
Do not assume an ordinary DVR HDD exposes video parity blocks. The software should discover redundancy, not 
assume it. The redundancy engine should handle: checksums/CRCs for validation; backup/duplicate indexes; 
secondary/sub-streams; RAID or explicit parity when the storage configuration actually provides it; and, only 
where the format is documented or experimentally proven, a known ECC/erasure-code reconstruction.
Redundancy discovery
  -> identify block/group mapping
  -> determine algorithm (if any)
  -> determine recoverability
  -> reconstruct missing block(s)
  -> verify against checksum/format/decoder
  -> record exact source of reconstruction
No-go rule: If there is no exposed redundancy and bits are physically absent, Hamming/XOR/Reed-Solomon 
cannot magically recreate the original bytes. AI may estimate visual content for a separate enhancement copy, 
but that is not exact evidence recovery.
9. Multi-Representation Recovery
Search the same evidence source for all surviving representations of an event: primary stream, secondary/sub-
stream, snapshots, thumbnails, indexes, timestamps and cached/exported copies. If the main stream is damaged 
but the sub-stream survives, use it for alignment, camera/time correlation and investigative context. Do not 
claim that upscaling a 480p sub-stream recreates the original 1080p pixels.
Main stream 1080p  -> damaged
Sub-stream 480p   -> intact

13. Device / Hardware Failure Handling
The product should diagnose and document device accessibility, but it should not pretend to replace a hardware 
recovery lab. If the device does not enumerate or has controller/media damage, produce an Evidence Health 
Report and stop destructive operations. Continue from a specialist-produced forensic image when available.
Device detected?
  YES -> read-only acquisition -> health test -> image -> verify
  NO  -> connection/driver diagnostics -> alternate read path if appropriate -> if still absent: hardware recovery required

16. Master Coding-Agent Prompt
Paste this into the coding agent you use. Force it to build phase-by-phase and stop when a gate fails.
You are the lead engineer for SIH26150, a forensic DVR/NVR evidence recovery platform. Build the product incrementally. Do NOT 
jump to UI polish before the recovery core works. Do NOT invent proprietary-format facts. Do NOT modify original evidence. Every 
phase must end with automated tests and a PASS/FAIL gate. If a gate fails, fix it before moving on.
PRODUCT PRINCIPLES
1. Read-only evidence handling; analyze forensic copies whenever possible.
2. Separate exact recovery, inferred recovery, and AI enhancement.
3. Generic recovery is the baseline; vendor/format parsers are validated plugins.
4. Never claim vendor-wide support from a single model.
5. Never fabricate missing bytes.
6. Preserve provenance for every recovered artifact.
7. Build a golden regression corpus with known ground truth.
BUILD PHASES
Phase 0: create project skeleton, test corpus manifest, threat/evidence-handling policy, and CI.
Phase 1: implement source detection, read-only checks, forensic image ingestion, SHA-256 hashing, acquisition log, and error 
handling.
Phase 2: implement volume/partition and filesystem inspection, raw byte reads, unallocated-region handling, and Evidence Health 
Report.
Phase 3: implement media fingerprinting, container/codec probing, timestamp extraction where available, and DVR-structure 
discovery hooks.
Phase 4: implement generic carving and contiguous-media extraction.
Phase 5: implement fragment database + candidate adjacency graph. Use channel/codec/metadata compatibility as filters; use 
timestamps and structure as evidence; require decode verification for accepted joins.
Phase 6: implement corruption repair for truncated containers, missing indexes, and partial clips. Output clean segments and 
explicit gaps.
Phase 7: implement Redundancy Analyzer. Detect checksums, duplicate indexes, sub-streams, RAID/parity/ECC only when the 
evidence exposes them. Implement mathematical reconstruction only after the redundancy layout is proven by a format 
adapter/test fixture.
Phase 8: implement parser registry and one real validated vendor/model/firmware adapter. Add a second only after the first is 
stable.
Phase 9: build case/timeline/search/viewer/reporting UI around the working core.
Phase 10: add optional AI for fragment ranking, quality assessment, search, and enhancement of copied outputs only.
Phase 11: harden security, negative tests, regression tests, performance, crash recovery, packaging.

21. Final Product Definition
The winning prototype is not “a player for every DVR.” It is a forensic recovery platform that starts from the 
storage layer, determines what evidence is actually present, extracts as much verifiable media as possible, 
repairs structurally damaged recordings where justified, preserves partial evidence instead of discarding it, and 
transparently tells the examiner how each result was obtained.
CORE USP
Vendor-agnostic evidence acquisition + deep storage analysis
+ generic media recovery
+ validated vendor/format adapters
+ corruption-aware reconstruction
+ partial evidence preservation
